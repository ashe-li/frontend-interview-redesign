1. 給 CEO／跨團隊：我們在改什麼、為什麼

這一節是給非前端、非技術背景的同仁讀的。一句話總結：我們現在用的面試題，AI 已經可以幫候選人秒答，所以分不出誰強誰弱了。新流程改成評估「人的判斷力」——這是 AI 取代不了、也正是這個職務的價值所在。

現況的問題

  • 流程老舊：現行兩份面試文件（Notion 上的「Frontend Interview」與「vocus F2E challenge」）是 2022–2023 設計的。實作題仍是「用 Next.js 做一個作者文章頁、SSR 帶出前四篇」，預期工時一天、用 AI 半天——這在今天已無法區分候選人能力高低。
  • AI 讓傳統題目失去鑑別力：研究顯示 40–50% 候選人在當前技術測驗能拿滿分；ChatGPT 數秒解掉多數 LeetCode 題；技術職位有 48% 候選人在面試中使用 AI 作弊。題目愈「標準」，愈分不出真實能力。
  • 禁用 AI 不是答案：到 2025 年底，70% 雇主已主動在面試測試 AI 流暢度。一味禁止只會讓作弊轉入地下、更難辨識。主流做法是「公開允許 AI、改評估使用 AI 的方式」。

我們改成什麼

核心轉向：不再問「你能不能把程式碼寫出來」（AI 都能寫），改問「你能不能判斷這段程式碼對不對、該不該這樣設計、AI 給錯時你看不看得出來」。

引用 Google Chrome 工程領導 Addy Osmani 的觀點：AI 會放大既有的工程品質——基礎強的人獲得複合優勢，基礎弱的人則是「混亂被加速」。我們要找的是判斷力強的人，不是打字快、或 token 燒得多的人。

  • 履歷階段就收結構化問答 + 一份 AI 開發成果，沒填的履歷參考價值低（直接提升初篩品質）。
  • 實作題允許並鼓勵用 AI，但要求附上使用的 prompt；交件後一定接一場 live 對談，請候選人親口解釋每個決策——這能分離「AI 寫的」與「候選人真的懂的」。
  • 新增「Code Review 反向題」：給一段 AI 產生、藏有缺陷的程式碼，請候選人挑錯。這比「叫他寫程式」更難作弊，也最貼近 vocus 日常工作。
  • 系統設計題改用 vocus 真實情境（文章頁快取策略、Web Vitals 劣化診斷），考架構判斷力。

順帶解決 / 可宣傳的點

  • 招募賣點即專業宣傳：JD 明寫「兩週一次與外部 SEO 顧問會議」「AI 工具費用可核銷」「內部自建 Skill／Agent 系統」——這些同時是吸引人才與對外展示專業度的素材。
  • 公平與可稽核：採結構化 rubric 評分。研究顯示結構化面試讓被拒候選人滿意度提升 35%、預測效度高於非結構化面試 34%，也降低偏誤與法律風險。

前端工程師 Frontend Engineer（AI-Native / SEO-Aware）

嗨！歡迎來到 vocus

vocus 方格子是台灣最大的內容創作與知識變現平台，並計畫持續拓展東南亞等國際市場。我們以「創作至上」為核心價值，打造讓創作者自由發表、累積影響力並獲得實質收益的創作生態圈。平台從圖文、訂閱、數位商品，到線上與實體的講座、活動，匯聚各領域創作者，提供多元的內容形式。

團隊文化

我們由熱愛內容、重視創意、樂於學習與分享、也重視數據與成果的夥伴組成。鼓勵開放溝通、強調協作；身在瞬息萬變的數位內容產業，我們也擁抱變化與挑戰、做好持續成長的準備。加入 vocus，你會與一群專業且樂於分享的夥伴，一起為更好的創作願景與內容平台努力。

Your career with vocus

作為 vocus 的前端工程師，你將是一位具備 SEO/AIO/GEO 意識的前端鬥士！從加入的第一天起，你會參與專案從立案到上線的完整流程，與 PM、設計師、前後端夥伴密切合作，用你的前端專業為每個挑戰提供建議。我們希望你能主動發掘問題、在需要時統整修正方向，與團隊一起討論最佳解法——把 SEO 的血液流在身心，寫出更有詩意且高效的程式碼！

主要職責

  • 開發 vocus 前端功能，提供流暢且豐富的服務體驗
  • 維護全站 SEO 品質：與外部顧問定期檢視指標，負責頁面效能、Accessibility、Web Vitals 調校與監控；在開發前期就給予 SEO/GEO 建議與把關
  • 與工程團隊優化系統架構與開發流程：與後端協作進行 API 架構優化，以及監控、報錯、Issue Tracking
  • 以前端專業與 PM、設計師討論新功能方向並評估可行性
  • 撰寫易維護、高可讀性的程式碼，參與 Code Review
  • 善用 coding agent（Claude Code、Cursor、Copilot 等）加速開發、code review 與文件產出，並持續優化團隊的工具輔助開發流程

具備條件（必備）

  • 精熟 React / Next.js 運作原理：理解 rendering model（SSR/SSG/ISR/CSR 的取捨）、元件生命週期與資料流，而非僅記憶 API
  • 紮實的 JavaScript / TypeScript 基礎：能判斷程式碼（含 工具產出）的正確性、效能與安全性
  • 熟悉狀態管理（SWR / Redux / React Context）與樣式方案（Tailwind CSS / Radix UI / styled-components）
  • SEO / Web Vitals（LCP / INP / CLS）/ Accessibility 的實作與調校經驗，並具備 GEO（生成式引擎優化）意識
  • 熟悉前端測試框架（Jest / Playwright），能針對情境撰寫測試
  • 熟悉 Git 與 Git Flow；能透過 Swagger 文件串接後端 API
  • 以 coding agent 協作為日常工作流：能設計 prompt／context、能 review 並驗證工具產出、知道何時不該用，並有一套自己的開發 workflow
  • 具備閱讀程式原始碼與技術文件的能力與習慣

擁有這些會很加分

  • 前端系統設計、組織大型專案結構的經驗
  • 帶領小型團隊、Mentor 工程師，或主導技術決策與流程優化的經驗
  • 用 coding agent 大幅提升效率的具體案例（元件生成、自動化測試／重構、PoC 加速、文件自動產出）
  • 用 AI 工具跨領域的經驗（非慣用程式語言開發，或行銷／設計／法務／財務等跨領域應用）
  • 熟悉 CI/CD 建置流；具 SEO 調校深度經驗
  • 樂於研究與學習，享受與夥伴一起分享交流
  • 過往工作或作品與內容產業相關

技術環境和我們工作的方式

  • 主站以 Next.js 為基礎，運行在 AWS EKS（Kubernetes），前面接 Cloudflare CDN／Tunnel；透過 CI/CD pipeline 自動 build／deploy
  • 可觀測性走 Grafana / Prometheus / Loki，前端的效能、報錯與 Web Vitals 都在這套體系監控
  • 你會在這個雲原生環境裡，特別關注 SSR／CDN 快取／rendering 策略對 SEO 與 Web Vitals 的影響
  • 兩週一次與外部 SEO 顧問會議：與業界專家定期切磋，持續精進平台 SEO/GEO 專業
  • 工具費用可核銷：我們鼓勵主動嘗試、評估並把對的工具帶進團隊；團隊也有內部自建的 Skill 與 Agent 系統
  • 面試就用我們平常的工作方式：技術面是一場現場 live AI pairing coding——帶你慣用的工具（Claude Code／Codex 等）和我們一起解題，重點看你的協作、判斷與驗證。

我們對你的期許：人的價值放在第一位

vocus 是創作者平台，前端的每一個頁面與互動都直接影響創作者與讀者的體驗。這個角色的價值，在於你對使用者體驗的判斷、對 SEO 與效能的把關、對棘手問題的排查，以及與 PM、設計、後端協作把功能做對做好的能力——這些是任何工具都無法取代的。我們的文化是積極擁抱新工具與新做法，把時間留給更有價值的事：

  • 到職第 2 個月：熟悉團隊現有工作流程與工具（包含內部 AI Agent、Skill、coding agent workflow），能穩定支援日常前端開發。
  • 到職第 4 個月：能獨立優化自己負責領域的開發流程（含工具輔助的測試、重構、文件、code review），主動找到更好的做法，把更多時間留給體驗設計、效能調優與棘手問題解決，並與團隊分享你發現的新做法。

我們看重的不是你用什麼工具，而是你有沒有「持續找到更好做法」的習慣。

  • coding agent 與 AI 工具：ChatGPT（Codex）、Claude（Claude Code），以及團隊自建的 Skill 與 Agent 系統

3. 新版面試流程設計（漏斗 + 各關卡理由）

設計原則（皆有研究支撐，來源見第 8 節）：① 公開允許 AI、改評估使用方式；② 用最貼近真實工作的題型（work sample + code review）取代抽象謎題；③ 每關都有「無 AI 反思」環節分離真實理解；④ 全程結構化 rubric 評分；⑤ 把 live 環節集中為單一 block，降低候選人時程負擔、加快 time-to-offer。

逐關設計

S0 — 履歷 + 結構化問答 + AI 作品（初篩）

  • 收什麼：履歷 + 四個簡答（見第 5 節）+ 一份引以為傲的成果（repo／demo／短片，或公司專案的去識別化說明）+（選填）AI 使用證據（ccusage 月報／web 對話截圖／常用 prompt 皆可，不需公司帳號）。
  • 怎麼篩：先看四個簡答與作品。沒有填寫問答的履歷，參考價值低、列為低優先。
  • 研究依據：2026 招募已從「who you are」轉向「what you have shipped」；GitHub／Demo／DECISIONS.md 是高訊號素材。

沒有可分享資料怎麼辦：核心漏斗是「有在用 AI → 有使用脈絡 → 聊得出怎麼用更好」。但不是每個人都有公開作品或可匯出的用量（公司帳號不能匯出、只用網頁版、NDA）。因此作品與用量一律選填、任何形式皆可、不需公司帳號；真正公平的共同關卡是 S2 live AI pairing——即使應徵階段完全沒資料，也能在現場直接產生可觀察的 AI 使用過程，再據此討論「怎麼用更好」。不因「沒資料」淘汰任何人（真正的初篩門檻是四個簡答有沒有認真填）。

S1 — 角色對齊面談（30 分，HM/Recruiter）

  • 目的：確認求職動機、溝通表達與團隊文化契合，並對齊角色期待與實際工作方式（含跨職能協作與會議節奏）。
  • 走過候選人的四個簡答、作品與（若有）ccusage 脈絡。
  • 賣點輸出：外部 SEO 顧問會議、AI 工具核銷、creator-first 文化、內部 Skill/Agent 系統。

S2 — Live AI pairing coding（現場 ~45 分）

  • 形式：螢幕共享，候選人用自己平常的工具（Claude Code／Cursor／Copilot），面試官當 pair partner + 觀察者。同一個 starter repo（已備好、故意埋 client-fetch）。重新設計的 F2E challenge，完整協定、starter repo、curveball 階梯、觀察 rubric 見第 5 節。
  • 為何改 live：現場觀察讓作弊問題直接消除，且看得到 async take-home 看不到的——prompt 顆粒度、AI 出錯時的反應、驗證習慣。重點從「成品」轉成「過程」。
  • 分段：暖身 5 分 → 核心 SSR/OG 20 分 → curveball 加碼 10 分 → 關 AI 反思 10 分（反思環節取代舊版的 take-home 後追問）。
  • 研究依據：Shopify（自帶工具、破損 repo、刻意讓 AI 產生垃圾以觀察反應）、Meta（prompt 顆粒度）、Anna McDougall（do-then-reflect、螢幕共享、ascending difficulty + reflection）。

S3 — Live 技術深談（60 分，兩段）

段落時間 / AI做什麼為何有效
3b Code Review 反向題 30 分 / 允許 給一段 AI 生成、藏缺陷的 Next.js PR（題庫見第 5 節），請其挑錯並說明會留什麼 comment 「批判程式碼」比「生成程式碼」更難作弊，最貼近日常工作
3c 系統設計 + 無 AI 反思 30 分 / 禁用 vocus 真實場景討論（快取／rendering 取捨）+ 純口頭確認底層知識 無 AI 環境驗證「沒有工具時的底層能力」，避免純 AI 操作員

S4 — 跨職能協作 + 文化面（45 分）

Senior IC 加嚴 bar（高於一般職等的門檻）

    能主導技術方向：自己辨識約束 → 提出取捨 → 推動落地（例：Vercel 不支援 persistent WebSocket → 改 SSE ＋ 共享 state store）。負向：遇到不熟的領域（如 Docker／後端）整包丟給 AI、被動接受工具產出而沒有自己的方案，是 operator 不是 driver。

S3b 範例題（讀 3 分鐘 / 解 10 分鐘）：抽 helper 後的沉默回歸

此題抽象自 vocus-web-ui 真實 P0（article-SSR helper 抽取造成死碼回歸，PR #7102 → #7600）。Extract Function 時 helper 在「不適用」case 仍回傳 truthy 值，caller 的 if (result) 永遠成立、殺掉 fallback → 舊文章靜默 render 錯誤、happy path 測試全綠。正是 AI 抽 helper／重構最常引入、且 quick review 看不出的 bug——考的不是「能不能寫」，是「能不能看穿」。

對應 rubric：D3 判斷力（主）／D1 底層／D2 review 工具產出。工具政策：可開放，但計分重點在「能否口頭說清楚為什麼是 bug」，不是貼修法。

給候選人的程式碼

// utils/article/prepareArticleContent.js
// 把文章資料整理成 SSR 要用的 [html, toc]
export function prepareArticleContent(article) {
  // case A：已發佈且有結構化內容
  if (isPublished(article) && article.contentObj) {
    const { html, toc } = renderFromObj(article.contentObj);
    return [html, toc];
  }
  // case B：純草稿
  if (article.draftObj) {
    const { html, toc } = renderFromObj(article.draftObj);
    return [html, toc];
  }
  // case C：兩者皆無（舊資料 / 空文章）→ 交給後面的 fallback 處理
  return [article, []];
}
// pages/article/[id].js  （getServerSideProps 內）
const result = prepareArticleContent(article);
if (result) {
  const [html, toc] = result;
  return { props: { html, toc } };
}

// fallback：舊資料用預設 renderer，並重新掃 heading 產生 TOC
const html = renderDefault(article);
const toc = buildTocFromHtml(html);
return { props: { html, toc } };

題幹線索：「published 文章和草稿都正常，但站上一批舊文章內文變成亂碼、目錄(TOC)永遠空白。單元測試全綠。請找出原因並修。」

預期答案（10 分鐘內）

  1. 定位：case C return [article, []] 是非空陣列 → truthy。caller if (result) 三種 case 都成立，fallback（renderDefault + buildTocFromHtml）變死碼；舊文章把整個 article 物件當 html（render 成亂碼），TOC 拿到 []。
  2. 修法（最小且最穩）：helper「不適用」case 改回傳 falsy 的 null（或 undefined），caller 維持原本的 if (result) 即可——合法回傳一律是陣列（恆 truthy），falsy 就落到 fallback，caller 一行都不用改。
    陷阱：若回 undefined 卻把 caller 改成 if (result !== null)，undefined !== null 為 true → 解構 undefined 直接 throw；!== null 只能配 null。

評分（1–4，行為錨定）

分數行為
1看不出問題，或只說「再加個 if 擋 case C」沒打到 truthy 根因
2找到 case C 有問題，但用 if (result.length) / if (result[0]) 等脆弱修法
3正確指出「truthy 回傳殺掉 fallback」，case C 改回 falsy（null/undefined）讓 if (result) 落到 fallback
4加上：說得出「為什麼測試全綠卻線上壞」（happy path 不覆蓋 case C）、指出 [article, []] 用同一 array shape 裝不同語意是 type smell、主動說要補 case C 單元測試

現場延伸追問（anti-cheat，AI 事先猜不到）

「如果我再加 case D：文章同時有 contentObj 和 draftObj，你的 helper 簽章要怎麼改，才能讓這類『不適用／衝突』情況不會再被 caller 誤判成成功？」

好的候選人會把回傳型別從 [html, toc]（truthy 陷阱）改成可明確區分的形狀（如 { status, html, toc } 或 discriminated union），而不是再靠陣列——驗證他有沒有把根因一般化，而不只補一個 if。

備援題（可輪替避免外流被背，皆 KB 真實案例）：① logger console.error(err) 經 pino override 變 [object Object]、stack 全丟 → 線上錯誤無法 debug（考錯誤序列化／觀測性意識）；② SSR catch 把 error.stack 塞進 redirect URL + 回 307 而非 notFound: true → 內部路徑/SQL 外洩 + SEO 持續索引壞網址（考安全 + SEO + HTTP 語意，稍難版）。

        <title>{article?.title ?? "vocus"}</title>
        <meta property="og:title" content={article?.title ?? ""} />
        <meta property="og:description" content={article?.abstract ?? ""} />
      </Head>
      {article ? <ArticleBody data={article} /> : <Spinner />}
    </>
  );
}

線索：瀏覽器看正常，但 (a) Search Console 抓到內文空、(b) FB/LINE 分享卡標題摘要全空、(c) DevTools disable JS 後整頁空白。

預期：資料只在 useEffect（client-only）抓，SSR 當下 article 為 null → server HTML 沒內文、OG 也空 → 爬蟲／社群 unfurl／no-JS 三者同源。修法：抓取移到 getServerSideProps（或 ISR），server 端填好資料與 OG。

通過門檻：指出「資料只在 client 抓、SSR 是空殼」+ 移到 server。滿分：三症狀同源、OG 必須 server-render、改 SSR 後注意快取（個人化 vs 公開）。

S3b 範例題 3：個人化內容被 CDN 公開快取（cache / 隱私）

出處：PDT-10007 subscriber-only、CF cache HIT 誤判、restore-95-cache-hit、cache-rule AND-condition 靜默失效 pattern。對應 rubric：D3 判斷、D4 系統、安全意識。

// pages/article/[id].js  (getServerSideProps)
export async function getServerSideProps({ params, req, res }) {
  const user = await getUserFromCookie(req);                   // 可能是登入者
  const article = await fetchArticle(params.id, { as: user }); // 帶個人化 / subscriber-only

  // 「加速重複請求」
  res.setHeader("Cache-Control", "public, s-maxage=600, stale-while-revalidate=60");

  return { props: { article, isSubscriber: user?.isSubscriber ?? false } };
}

線索：subscriber 專屬內容偶爾被非訂閱者看到；有時 A 使用者看到 B 的個人化區塊；CF cf-cache-status 多為 HIT。

預期：對「帶登入者、含 subscriber-only」的回應設了 public, s-maxage → CF edge 快取第一個人的個人化 HTML 發給所有人 → 權限/隱私外洩。修法：個人化回應一律 private, no-store；或「公開外殼 SSR（可快取）+ 私有片段 client 端抓」。

通過門檻：指出「個人化內容設 public 快取 → 跨使用者外洩」+ 改 no-store/private。滿分：權衡整頁 no-store 殺命中率 → 公開殼 + 私有片段折衷，並提 subscriber-only 對爬蟲的呈現。這也是 AI 最常為「優化效能」亂加 cache header 卻忽略個人化的 bug。

S3b 範例題 4：不能用鍵盤操作的「按鈕」（a11y）

出處：a11y 為職務明列具備條件；a11y-test-via-aria-graph、a11y-audit-finding-triage pattern。對應 rubric：D1 底層（a11y）、D3 判斷。

function ShareBar({ onShare, onBookmark }) {
  return (
    <div className="share-bar">
      <div className="icon-btn" onClick={onShare}>
        <ShareIcon />
      </div>
      <button className="icon-btn" onClick={onBookmark}>
        <BookmarkIcon />
      </button>
    </div>
  );
}

線索：鍵盤使用者無法 focus、按 Enter 觸發不了分享；螢幕報讀器把書籤鈕只念成「按鈕」；Lighthouse a11y 掉分。

預期：(1) 分享用 <div onClick> → 不可 focus、無鍵盤事件、無 role；(2) 兩顆 icon-only 按鈕都沒有 accessible name。修法：分享改回原生 <button>；兩顆都補 aria-label（或 sr-only 文字）。

通過門檻：抓到「div 當按鈕不可鍵盤操作」或「icon button 無 label」其一。滿分：兩者都抓、首選原生 <button> 而非補一堆 ARIA、並指出「a11y 測試要走 ARIA tree（accessible name/description）而非只斷言屬性存在」。

S3c 系統設計 + 無 AI 反思題（vocus 真實場景）

  • 「設計 vocus 文章頁的快取策略：subscriber-only 內容用 SSR / ISR / CSR 如何取捨？CDN 層怎麼配？」
  • 「文章頁 Web Vitals（LCP / INP / CLS）劣化時，你的診斷 SOP 是什麼？」
  • 「AMP 文章頁的 CF 快取要注意什麼？」
  • 無 AI 純口頭：RSC（Server Component）執行邊界、INP 優化思路、Cache-Control 語意——確認可獨立判斷的底層知識。

6. ccusage / token 用量信號：建議用法與風險（決策依據）

你筆記中提到希望候選人提供「最投入的一個月」連續 token 用量（參考 ccusage）。這點值得做，但怎麼用決定它是助力還是地雷。以下是中立的正反依據與建議。

ccusage 是什麼

ccusage（ryoppippi 開發）是本地 CLI，分析 Claude Code／Codex／Copilot CLI／Gemini CLI 等的 token 用量與成本，資料來自本地 JSONL、不上傳雲端，可出日／週／月報。它沒有官方分享或團隊比較功能，定位是個人成本管理工具——意即提交的截圖可被候選人自行編輯，無第三方驗證。

正反論點

支持（可作信號）反對（作篩選條件的風險）
用量反映 AI 採用深度與投入度（Nvidia 黃仁勳提「token 作為薪酬第四支柱」） Goodhart／tokenmaxxing：Meta 內部排行榜出現「燒 281 億 token 卻零生產力」；指標一旦成為目標就失效
「token 效率」（少量達標）或可作問題框架化品質的代理 效度背離：22,000 開發者數據顯示 AI 高用量伴隨缺陷率 +54%、code churn +861%；token 是輸入非成果
業界確有公司追蹤 AI 使用數據 易 gaming：分割 session、灌長 prompt、重跑 agent 都能膨脹數字，且 ccusage 無法驗真偽
可作為面談的「脈絡開場」素材 公平性：Claude Pro $20 vs Max $100/$200 額度差 5–10 倍，用量高可能只代表「工具買得起」
— 隱私／法律：要求提交個人使用日誌涉個資；AI 輔助決策若致歧視結果，雇主仍負全責
  • 建議做法：收，但只當脈絡，不以數字評分
    在 JD 標示「選填、鼓勵」，且接受任何形式的使用證據（ccusage／web 對話截圖／常用 prompt，不需公司帳號），避免只認 CLI 用量造成的不公平。面談時請候選人口頭解釋「用了什麼、用在哪、如何驗證」。沒有可分享資料者不扣分——由 S2 live AI pairing 現場產生可觀察的使用過程補足，解決「沒資料就無從討論」。評估的是 AI 協作的深度與判斷，不是 token 數字。
  • 避免：以 raw token 總量排序或設門檻
    會誘發灌量、加劇工具取得的不平等，且與真實貢獻相關性低（Meta／Faros.ai 已驗證）。低用量不該扣分，高用量不該加分。
AI 會放大既有的工程判斷力。評估目標是找「判斷力強的人」，而不是「token 燒得多」或「prompt 寫得快」的人。
